# Qwen3.6-35B-A3B 6000ws Worker-Verifier Logprob Comparison Experiment Report

This report is compiled separately from the Qwen3.6-35B-A3B verifier results under the
`experiments/logprobs/data/qwen3.6-35b-a3b/` directory. What the repository provides is the
verifier recomputation output (CSV/summary/metadata); the raw worker evidence `.jsonl` and its
data package are intermediate artifacts and are not shipped with the repository.

- verifier results directory: `experiments/logprobs/data/qwen3.6-35b-a3b/`
- BF16 verifier: `6000ws_worker_vs_6000ws_verifier_qwen3.6-35b-a3b-bf16`
- FP8 verifier: `6000ws_worker_vs_6000ws_verifier_qwen3.6-35b-a3b-fp8`
- worker evidence (not provided): `worker_evidence.6000ws_long_first.jsonl`

## 1. Summary of Conclusions

The core question of this round of experiments is: on the 6000ws machine, can the
`input + output + logprob trace` generated by a `Qwen/Qwen3.6-35B-A3B` BF16 worker be stably
replayed by a same-model BF16 verifier; and does the corresponding FP8-quantized verifier exhibit
a distinguishable logprob fingerprint difference.

The current data supports the following conclusions:

1. **The same-model BF16 verifier can serve as the baseline for this round of Qwen3.6-35B-A3B, but the baseline itself has a pronounced long-tail outlier.**
   - `BF16 worker -> BF16 verifier`: `abs_logprob_diff mean = 0.0591`, `p50 = 0.000606`, `p95 = 0.1432`, `p99 = 0.4331`.
   - However, the same-model baseline has `p999 = 11.1895` and `max = 24.1029`, indicating a small number of very large token-level drifts.
   - Therefore, in this experiment the single-token `max` or extreme tail should not be treated as the primary decision criterion.

2. **The FP8 verifier exhibits a systematic offset relative to the BF16 verifier, and is consistently worse across the bulk-to-p99 range.**
   - `BF16 worker -> FP8 verifier`: `abs_logprob_diff mean = 0.0848`, `p50 = 0.001088`, `p95 = 0.2278`, `p99 = 0.6729`.
   - Relative to the BF16 baseline, FP8's `mean/p50/p90/p95/p99` are approximately `1.44x/1.80x/1.65x/1.59x/1.55x`.
   - `rank_delta_rate` rises from `2.51%` to `3.64%`, roughly `1.45x`.

3. **The main evidence for FP8 is not a larger max, but a wider overall distribution and worse top-k distribution consistency.**
   - `p999` and `max` only increase from `11.1895/24.1029` to `12.6798/27.5559`, a ratio of only `1.13x/1.14x`.
   - But `topk_jaccard_mean` drops from `0.8922` to `0.8449`.
   - `topk_jaccard_p05` drops from `0.7297` to `0.6842`.
   - `union_js_p99` increases from `0.0582` to `0.1165`, roughly `2.00x`.

4. **After aggregating by sample, FP8 is also more prone to high-drift samples than the BF16 baseline.**
   - Number of samples with `sample mean_abs_logprob_diff > 0.2`: BF16 `18/300`, FP8 `42/300`.
   - Number of samples with `sample p99_abs_logprob_diff > 0.5`: BF16 `76/300`, FP8 `125/300`.
   - Number of samples with `sample p99_abs_logprob_diff > 5.0`: BF16 `11/300`, FP8 `21/300`.
   - This shows that the FP8 difference is not driven by just one or two extreme tokens, but is visible across more sample windows.

5. **The current data does not observe any monotonic error accumulation caused by input length or output depth.**
   - BF16: `corr(input_len, abs_diff) = 0.0350`, `corr(depth, abs_diff) = -0.0543`.
   - FP8: `corr(input_len, abs_diff) = 0.0336`, `corr(depth, abs_diff) = -0.0602`.
   - The bucket results also do not exhibit a simple monotonic trend of "longer is worse" or "deeper is worse".

6. **This is still statistical verification, not a single-token proof.**
   - For an MoE model like Qwen3.6-35B-A3B, this round's same-model baseline already shows heavy-tailed outliers.
   - Production decisions should use window-level aggregate metrics, e.g. `mean/p95/p99 abs_logprob_diff + rank_delta_rate + top-k overlap/JS`, rather than a single-token threshold.

The verifier does not re-decode; instead it concatenates the worker's already-recorded `input_ids + output_ids` into a complete token prompt, then lets vLLM perform full-prefill prompt logprobs.

```text
vllm_prompt_logprobs_full_prefill
```

The verifier alignment position for each output token is:

```text
prompt_pos = input_token_count + output_depth
```

So all `depth` values in this report denote output token depth:

- `depth = 0`: the 1st output token
- `depth = 1`: the 2nd output token
- and so on

There are two verifiers in this round:

|---|---|---|---|---|---:|---:|---:|---:|---:|---:|

Both verifiers satisfy:

```text
missing verifier selected logprob = 0
skipped_too_long = 0
```

This means the verifier found the logprob of the worker's selected token at every output depth.

### 2.3 Tokenizer Considerations

The BF16 verifier's tokenizer hash in the metadata is:

```text
45f8cf25137775ed
```

The FP8 verifier's tokenizer hash is:

```text
572cd96959d809c1
```

This hash includes the tokenizer's `name_or_path` and other local state, so different model paths may produce different hashes. At actual verifier runtime, the `input_ids + output_ids` already recorded in the worker evidence are used, rather than re-encoding text with the FP8 tokenizer.

Therefore the premise of this round's comparison is:

```text
Qwen3.6-35B-A3B and Qwen3.6-35B-A3B-FP8 have compatible token id spaces
```

Under this premise, comparing the selected token logprob and top-k distributions is meaningful.

### 2.4 Relationship Between Logprob and Logits

What this experiment actually compares is the **logprob** exposed by vLLM, not raw logits.

logprob can be understood as the result of applying log-softmax to logits:

```text
logprob(token_i) = log_softmax(logits)[token_i]
```

Therefore the conclusions of this report should be phrased as:

```text
the worker-verifier logprob fingerprint can distinguish the statistical difference between the BF16 verifier and the FP8 verifier
```

rather than:

```text
it has been directly proven that the full distribution of raw logits is completely distinguishable
```

## 4. Metric Definitions

### 4.1 abs_logprob_diff

The core scalar metric:

```text
abs_logprob_diff = abs(worker_selected_logprob - verifier_selected_logprob)
```

It measures how much the selected logprob the worker gives for that output token differs from the selected logprob recomputed by the verifier's full-prefill.

### 4.2 Percentile

The `p50/p90/p95/p99/p999` in the tables are the percentiles of `abs_logprob_diff` over all output depth rows.

Recommended focus:

- `p95`: routine tail drift
- `p99`: strong tail drift
- `p999`: extreme but still more stable tail drift than `max`

This round's Qwen3.6-35B-A3B baseline has a pronounced heavy tail, so using `max` alone for decisions is not recommended.

### 4.3 rank_delta_rate

```text
rank_delta_rate = fraction(rank_delta_verifier_minus_worker != 0)
```

It represents how many output tokens have a selected token rank that changes between the worker and the verifier.

### 4.4 topk_jaccard

Each output depth has a worker top-k token set and a verifier top-k token set. The Jaccard overlap is defined as:

```text
Jaccard = |worker_topk ∩ verifier_topk| / |worker_topk ∪ verifier_topk|
```

This round's top-k is top-32. The lower the `topk_jaccard_p05`, the worse the tail token set overlap.

### 4.5 union_js

`union_js_divergence` aligns the token union of the worker top-k and verifier top-k, then computes the Jensen-Shannon divergence over the probability distributions.

It measures not only the selected token, but whether the local top-k distribution as a whole is similar. The larger the value, the greater the distributional difference.

## 6. Same-Model BF16 Baseline Analysis

### 6.1 The Same-Model Baseline Is Not Zero Error

The overall error of `BF16 worker -> BF16 verifier` is very low, but not zero:

| metric | value |
|---|---:|
| mean | 0.0591 |
| p50 | 0.000606 |
| p90 | 0.0807 |
| p95 | 0.1432 |
| p99 | 0.4331 |
| p999 | 11.1895 |
| max | 24.1029 |
| rank_delta_rate | 0.0251 |

This shows that for Qwen3.6-35B-A3B, this round's same-model envelope contains at least two kinds of phenomena:

1. The logprob diff of most tokens is very small.
2. A small number of tokens exhibit a very large selected logprob diff, accompanied by a large rank change.

The largest BF16 baseline outliers in `summary.md` include:

| sample | depth | token | worker lp | verifier lp | abs diff | rank |
|---|---:|---|---:|---:|---:|---|
| `21e9f9b29eb59f962703` | 6 | `The` | -0.0847 | -24.1876 | 24.1029 | 1/3103 |
| `aa2d2f1274b0d99eee0e` | 7 | ` aims` | -0.5754 | -23.1630 | 22.5875 | 1/19545 |
| `5ade7d1684a8dc883a00` | 7 | ` arg` | -0.5951 | -21.7985 | 21.2034 | 1/6827 |
| `a60ee7075a0a152bc3f3` | 8 | ` depth` | -0.0099 | -21.1415 | 21.1315 | 1/9322 |
| `ef63ae0b76a298deb773` | 13 | `ISO` | -0.1629 | -19.9728 | 19.8099 | 1/2657 |

Most of these outliers are isolated token-level events, and they already exist in the BF16 baseline itself. A reasonable explanation is that there are numerical/scheduling differences between the vLLM decode generate path and the full-prefill prompt logprobs path; for MoE models, routing or kernel path differences may also be superimposed. This explanation is inferred from the result patterns, not a root cause that this experiment directly located.

### 6.2 The Decision Significance of the Baseline

The value of the BF16 baseline is not that "the error should be 0", but that it gives the same-model drift envelope under the current model, current GPU, current vLLM version, and current prompt distribution.

Under this round's data, a fairly reliable description of the baseline is:

```text
the selected logprob diff of the vast majority of tokens is very small,
but same-model replay also permits a small number of extreme outliers.
```

Therefore, when later judging FP8 or other variants, one should look at whether the overall distribution systematically widens, rather than only looking at the largest token.

## 7. FP8 Quantized Verifier Analysis

### 7.1 Main Differences Between FP8 and the BF16 Baseline

The FP8 verifier's differences manifest mainly at three levels:

1. Larger selected token logprob diff:
   - `mean` increases from `0.0591` to `0.0848`.
   - `p95` increases from `0.1432` to `0.2278`.
   - `p99` increases from `0.4331` to `0.6729`.

2. The selected token rank changes more easily:
   - `rank_delta_rate` increases from `2.51%` to `3.64%`.

3. The top-k local distribution is more inconsistent:
   - `topk_jaccard_mean` drops from `0.8922` to `0.8449`.
   - `topk_jaccard_p05` drops from `0.7297` to `0.6842`.
   - `union_js_p99` increases from `0.0582` to `0.1165`.

These three kinds of metrics move in a consistent direction, so the logprob fingerprint of the FP8 verifier versus the BF16 worker can be considered statistically separable.

### 7.2 FP8 Is Not Just a Few More Extreme Points

After aggregating by sample, FP8 also has more high-drift samples:

| sample-level condition | BF16 | FP8 |
|---|---:|---:|
| `mean_abs_logprob_diff > 0.2` | 18 | 42 |
| `mean_abs_logprob_diff > 0.3` | 10 | 18 |
| `mean_abs_logprob_diff > 0.5` | 4 | 7 |
| `mean_abs_logprob_diff > 1.0` | 2 | 3 |
| `p99_abs_logprob_diff > 0.5` | 76 | 125 |
| `p99_abs_logprob_diff > 1.0` | 45 | 64 |
| `p99_abs_logprob_diff > 2.0` | 28 | 50 |
| `p99_abs_logprob_diff > 5.0` | 11 | 21 |

This shows that FP8's offset does not come only from a few largest outliers, but that a wider error distribution can be seen across more sample windows.

### 7.3 The Strength of FP8's Separability

Compared with the large separation of FP8/AWQ/small models in the earlier Qwen3-32B report, this round's Qwen3.6-35B-A3B FP8 difference is more moderate:

- p95/p99 are roughly `1.55x-1.59x` of the BF16 baseline.
- rank_delta is roughly `1.45x`.
- union JS p99 is roughly `2.00x`.

This is sufficient to support statistical distinction, but is not suitable for a very aggressive single-metric hard threshold. A more robust approach is to use multi-metric joint scoring and to calibrate the false reject rate on holdout prompts.

## 9. How to Make Reliable Decisions

### 9.1 Single-Token Decisions Are Not Recommended

This round's BF16 baseline already has a same-model outlier of `max_abs_logprob_diff = 24.1029`. If a single-token max is used as a threshold, two problems arise:

1. Setting the threshold low will falsely flag the BF16 same-model baseline.
2. Setting the threshold high will weaken detection of moderate systematic offsets like FP8's.

### 9.2 Window-Level Aggregation Is Recommended

A more reliable decision method is to aggregate over one output window, e.g. a 32-, 64-, or full 128-token window, then use a multi-metric envelope:

- `mean_abs_logprob_diff`
- `p95_abs_logprob_diff`
- `p99_abs_logprob_diff`
- `rank_delta_rate`
- `topk_jaccard_mean`
- `topk_jaccard_p05`
- `union_js_p95/p99`

For this round's data, the difference between FP8 and BF16 is directionally consistent across multiple metrics, so a multi-metric combination is more robust than a single threshold.

### 9.3 Initial Threshold Recommendations Under the Current Data

If this is just an initial sanity check based on this round of experiments, one can use the overall distribution of the BF16 baseline as the envelope:

| metric | BF16 baseline | FP8 observed |
|---|---:|---:|
| token mean_abs | 0.0591 | 0.0848 |
| token p95_abs | 0.1432 | 0.2278 |
| token p99_abs | 0.4331 | 0.6729 |
| rank_delta_rate | 0.0251 | 0.0364 |
| topk_jaccard_mean | 0.8922 | 0.8449 |
| topk_jaccard_p05 | 0.7297 | 0.6842 |
| union_js_p99 | 0.0582 | 0.1165 |

A conservative decision strategy could be:

```text
reject only when multiple metrics deviate from the BF16 baseline simultaneously,
do not reject because of a single token outlier.
```

For example, if a verifier on the same batch of samples simultaneously exhibits:

- both `p95_abs` and `p99_abs` markedly exceeding the BF16 baseline;
- `rank_delta_rate` higher than the BF16 baseline;
- `topk_jaccard` dropping and `union_js` rising;

then it is more likely a model/quantization version difference than a single token's numerical outlier.

It is still recommended to recalibrate production thresholds with holdout data, and in particular to separately estimate:

- the BF16 same-model false reject rate;
- the FP8 false accept rate;
- the stability across different prompt categories and different input length buckets.

## 10. Boundaries of the Current Conclusions

### 10.1 Covers Only 6000ws Single-Machine Results

This report analyzes only `6000ws worker -> 6000ws verifier`. It does not cover:

- H100 or other GPUs;
- cross-GPU worker-verifier;
- multi-card tensor parallel;
- different vLLM versions;
- different batch sizes.

### 10.2 Covers Only the BF16 Worker

This round's worker evidence comes from the `Qwen/Qwen3.6-35B-A3B` BF16 worker. FP8 is tested only as a verifier.

Therefore this report cannot answer:

```text
whether evidence generated by an FP8 worker can be accepted by a BF16 verifier or an FP8 verifier
```

To answer this question, additional FP8 worker evidence must be collected.

### 10.3 This Is Not a Full Raw Logits Comparison

This experiment compares the selected/top-32 logprob, not the full-vocab raw logits. The top-k distribution metrics also cover only the top-32 exposed by vLLM.

Therefore top-k Jaccard and JS divergence are local distribution metrics, not full-vocab distribution metrics.

### 10.4 Differing Tokenizer Hashes Require Ongoing Attention

The tokenizer hashes of the BF16 and FP8 verifiers differ. Although this round's verifier uses the token IDs from the evidence rather than re-tokenizing text, if different model paths or different tokenizer files are to be mixed later, it is recommended to explicitly verify:

- whether the vocab size is consistent;
- whether the special token ids are consistent;
- whether the chat template affects any re-encoding flow;
- whether the token id to token string mapping is compatible.

### 10.5 Limited Prompt Distribution

This round's data is 300 prompts, 10 categories, 30 per category. Although it includes multiple input length buckets, it is still not a complete production workload.

In particular:

- low-margin tokens;
- structured output;
- ultra-long context;
- multilingual;
- code;
- MoE routing-sensitive samples;

these categories may all affect tail behavior, and sampling must continue to be expanded on the production distribution.

### 10.6 The Output Length Cap Is 128

The current output is at most 128 tokens, and many samples are truncated at 128 tokens. This report can only demonstrate that no obvious depth accumulation is observed under `max_new_tokens = 128`.

It cannot be extrapolated to 512, 1024, or longer generations.

## 11. Final Summary

This round of the 6000ws Qwen3.6-35B-A3B experiment shows:

1. `BF16 worker -> BF16 verifier` can establish a same-model baseline, but the baseline has a pronounced token-level long-tail outlier.
2. `BF16 worker -> FP8 verifier`, relative to the BF16 baseline, exhibits a systematic offset in `mean/p50/p90/p95/p99`, `rank_delta_rate`, `top-k overlap`, and `JS divergence`.
3. FP8's difference is mainly reflected in a widened overall distribution and reduced local distribution consistency, rather than simply a larger max.
4. The current data finds no obvious monotonic accumulation effect from input length or output depth.
5. For an MoE model like Qwen3.6-35B-A3B, window-level, multi-metric statistical decisions should be used, and single-token thresholds should not be relied upon.
