# Qwen3-8B BF16 Single-Sample Verifier Design

Goal: given a single `input + output + worker logprobs`, decide whether it looks like a dense logprob fingerprint produced by a `Qwen/Qwen3-8B` BF16 worker. The current thresholds jointly account for the re-computation results of both the 4090 verifier and the L4 verifier over the same batch of 4090 worker evidence.

The single-sample verifier does not produce a binary strong proof; instead it emits a three-state verdict:

- `PASS_SINGLE_STRICT`: the sample strictly matches the Qwen3-8B BF16 fingerprint.
- `REJECT_SINGLE`: the sample clearly does not match the Qwen3-8B BF16 fingerprint.
- `INCONCLUSIVE_SINGLE`: the sample falls in the gray zone; a single sample carries insufficient information.

The rationale for this design is that on easy samples FP8/AWQ can be very close to BF16 on the selected-token logprob; forcing a binary classification would raise both the false-pass and false-reject rates.

## Input Format

Each sample must contain:

| Field | Purpose |
|---|---|
| `input_ids` | Context prefix for verifier re-computation |
| `output_ids` | The output already generated by the worker; the verifier does a teacher-forced replay |
| `worker_trace[*].selected_logprob` | Worker's logprob for the selected token |
| `worker_trace[*].selected_rank` | Rank of the selected token within the worker's top-k |
| `worker_trace[*].top_logprobs` | Worker top-k logprob fingerprint |

If top-k is missing, only a coarse selected-logprob filter can be applied, and `PASS_SINGLE_STRICT` cannot be granted.

## Verifier Parameter Standard

| Parameter | Recommended value |
|---|---:|
| verifier model | `Qwen/Qwen3-8B` |
| quantization | `bf16` |
| dtype | `bfloat16` |
| trace mode | `vllm_prompt_logprobs_full_prefill` |
| prompt_logprobs | `32` |
| max_logprobs | `32` |
| missing_logprob | `-100.0` |
| temperature | `0.0` |
| top_p | `1.0` |
| top_k | `0` |
| verifier GPU | `4090` or `L4` |

The verifier does not re-decode; it pins the worker's output path:

```text
full_prompt_ids = input_ids + output_ids
prompt_pos = len(input_ids) + depth
target_id = output_ids[depth]
```

It then reads the verifier's logprob/rank/top-k for `target_id` at `prompt_pos`.

## Per-Token Metrics

For each output depth, compute:

```text
logprob_diff = verifier_selected_logprob - worker_selected_logprob
abs_logprob_diff = abs(logprob_diff)
rank_delta = verifier_selected_rank - worker_selected_rank
rank_mismatch = 1[rank_delta != 0]
topk_jaccard = |worker_topk ∩ verifier_topk| / |worker_topk ∪ verifier_topk|
union_js = JS(worker_topk_prob_on_union, verifier_topk_prob_on_union)
```

The per-token `max_abs_logprob_diff` is not used as a primary pass/reject condition, because the BF16 baseline itself can exhibit isolated outliers.

Here `rank_mismatch` is precisely the per-token event of "selected token rank disagreement".

## Per-Sample Aggregate Metrics

Aggregated over all output tokens of a single sample:

| Metric | Meaning |
|---|---|
| `finite_count` | Number of valid output tokens |
| `missing_selected_count` | Number of times the worker selected token is missing from the verifier top-k |
| `mean_abs_logprob_diff` | Mean selected-token logprob drift |
| `abs_logprob_diff_p95` | Selected-token p95 drift |
| `abs_logprob_diff_p99` | Selected-token p99 drift |
| `rank_delta_nonzero_rate` | Selected-token rank disagreement fraction, i.e. `mean(1[verifier_rank != worker_rank])` |
| `topk_jaccard_mean` | Mean top-k token-set overlap |
| `union_js_p99` | p99 JS divergence of the top-k union probability distribution |

`rank_delta_nonzero_rate` is exactly the selected-token rank mismatch rate. Neither `mean(rank_delta)` nor `max(abs(rank_delta))` is used as a primary metric here, because the sign and extreme values of the rank delta are easily affected by top-k truncation and near-tie tokens; the fraction of "whether a rank disagreement occurred" is more stable.

## PASS_SINGLE_STRICT Conditions

All must hold to pass:

| Metric | Condition |
|---|---:|
| `finite_count` | `> 5` |
| `missing_selected_count` | `== 0` |
| `mean_abs_logprob_diff` | `<= 0.018` |
| `abs_logprob_diff_p95` | `<= 0.100` |
| `abs_logprob_diff_p99` | `<= 0.200` |
| `rank_delta_nonzero_rate` | `<= 0.025` |
| `topk_jaccard_mean` | `>= 0.935` |
| `union_js_p99` | `<= 0.012` |

This set of thresholds is slightly looser than batch strict, but stricter than the previous provisional single-sample thresholds. After incorporating the L4 verifier results, the thresholds remain unchanged: the 4090 BF16 single-sample pass rate is about `89.6%`, and the L4 BF16 pass rate is about `86.5%`; the FP8 false-pass rate is about `1.0%` on the 4090 and about `1.5%` on the L4.

In the current calibration data, every sample has a `finite_count` of `128`, so setting the token-count threshold to `> 5` does not change the existing statistics; in production short-output scenarios it will let more samples enter the decision, but the confidence of short samples should be reinforced with additional probes or a batch verifier.

## REJECT_SINGLE Conditions

Any one being satisfied triggers a reject:

| Metric | Condition |
|---|---:|
| `missing_selected_count` | `> 0` |
| `mean_abs_logprob_diff` | `> 0.023` |
| `abs_logprob_diff_p95` | `> 0.130` |
| `abs_logprob_diff_p99` | `> 0.280` |
| `rank_delta_nonzero_rate` | `> 0.040` |
| `topk_jaccard_mean` | `< 0.910` |
| `union_js_p99` | `> 0.025` |

The reject thresholds are deliberately wider than the pass thresholds, leaving a gray zone for the legitimate numerical fluctuation of BF16; but compared with the initial version, it is more sensitive to FP8, keeping the FP8 `INCONCLUSIVE_SINGLE` rate in the current data at about `8.8%` while rejecting all of Qwen2.*-7B and AWQ.

After incorporating the L4, the BF16 single-sample reject rate rises from about `0.75%` on the 4090 to about `2.0%` on the L4. These rejects mainly come from isolated logprob outliers in a few samples or a slight top-k jaccard overshoot; therefore a single-sample reject should still be interpreted as "clearly unlike the current BF16 fingerprint, or in need of review", and high-confidence production decisions should aggregate multiple probes.

## Decision Order

```text
if all PASS_SINGLE_STRICT conditions:
    verdict = PASS_SINGLE_STRICT
elif any REJECT_SINGLE condition:
    verdict = REJECT_SINGLE
else:
    verdict = INCONCLUSIVE_SINGLE
```

`INCONCLUSIVE_SINGLE` is neither a pass nor a reject. In production it is recommended to add probes for such samples and then decide with a batch verifier.

worker-logits-collect-vllm-evidence \

The verifier difference between L4 and 4090 is far smaller than the model/quantization difference: genuine Qwen3-8B BF16 still concentrates at `mean_abs ~= 0.008-0.009`, `p95 ~= 0.05`, `p99 ~= 0.10`; the gap of FP8/AWQ/Qwen2.*-7B from BF16 remains clearly visible.

### Misclassification rate and posterior interpretation of the single-sample verdict

Two kinds of probabilities must be distinguished:

- `P(reject | BF16)`: the probability that, when the truth is BF16, the verifier judges it as `REJECT_SINGLE`. This is the BF16 false reject rate, i.e. the calibrated misclassification rate of "wrongly killing BF16".
- `P(BF16 | reject)` or `P(BF16 | pass)`: the posterior probability that the sample truly comes from BF16, after having already observed the verifier emit `reject` or `pass`. This is not a quantity that can be uniquely determined from the conditional rates in the table alone; it also requires a model prior.

If you only care about "whether BF16 will be wrongly killed", just look at `P(reject | BF16)`:

| verifier GPU | `P(reject | BF16)` | Meaning |
|---|---:|---|
| 4090 | `0.750%` | BF16 single-sample false reject rate under the 4090 verifier |
| L4 | `2.000%` | BF16 single-sample false reject rate under the L4 verifier |
| 4090/L4 equal-weight average | `1.375%` | Equal-weight estimate when not distinguishing verifier GPU |

This number answers: if a sample truly comes from `Qwen/Qwen3-8B` BF16, how likely is a single verifier pass to reject it. Since a single-sample reject may still come from an isolated outlier or a slight top-k difference, in production one should not interpret a single `REJECT_SINGLE` as a complete identity-attestation proof; high-confidence scenarios should aggregate multiple probes.

To answer "after seeing `reject`, how likely is it still BF16", use Bayes' formula:

```text
P(model_i | verdict) =
    P(verdict | model_i) * P(model_i)
    / sum_j P(verdict | model_j) * P(model_j)
```

When there is no business prior, one can start with an illustrative assumption: the four candidate models `Qwen/Qwen3-8B` BF16, `Qwen/Qwen3-8B-FP8`, `Qwen/Qwen3-8B-AWQ`, `Qwen2.*-7B` have equal priors, and the 4090/L4 verifiers are equally probable. Under this assumption, the single-sample equal-weight-averaged conditional rates are:

| Model | `P(pass | model)` | `P(reject | model)` | `P(inconclusive | model)` |
|---|---:|---:|---:|
| `Qwen/Qwen3-8B` BF16 | `88.0625%` | `1.375%` | `10.5625%` |
| `Qwen/Qwen3-8B-FP8` | `1.2500%` | `89.917%` | `8.833%` |
| `Qwen/Qwen3-8B-AWQ` | `0%` | `100%` | `0%` |
| `Qwen2.*-7B` | `0%` | `100%` | `0%` |

Under this equal-prior assumption, the posterior after observing a single `REJECT_SINGLE` is:

| Model | `P(model | reject)` |
|---|---:|
| `Qwen/Qwen3-8B` BF16 | `0.472%` |
| `Qwen/Qwen3-8B-FP8` | `30.868%` |
| `Qwen/Qwen3-8B-AWQ` | `34.330%` |
| `Qwen2.*-7B` | `34.330%` |

This shows that `REJECT_SINGLE` is strong evidence for "not BF16": under the above equal prior, the probability that it is still BF16 after a reject is about `0.47%`. But both AWQ and Qwen2.*-7B are at `100% reject`, so a single `reject` from this verifier alone cannot distinguish them; the posterior ratio between them is determined entirely by the prior.

If the verifier GPU is known, the `reject` posterior differs slightly:

| verifier GPU | BF16 | FP8 | AWQ | Qwen2.*-7B |
|---|---:|---:|---:|---:|
| 4090 | `0.258%` | `30.994%` | `34.374%` | `34.374%` |
| L4 | `0.686%` | `30.743%` | `34.286%` | `34.286%` |

Similarly, under the equal-prior, 4090/L4 equal-weight assumption, the posterior after observing a single `PASS_SINGLE_STRICT` is:

| Model | `P(model | pass)` |
|---|---:|
| `Qwen/Qwen3-8B` BF16 | `98.600%` |
| `Qwen/Qwen3-8B-FP8` | `1.400%` |
| `Qwen/Qwen3-8B-AWQ` | `0%` |
| `Qwen2.*-7B` | `0%` |

If the verifier GPU is known, the `pass` posterior is:

| verifier GPU | BF16 | FP8 | AWQ | Qwen2.*-7B |
|---|---:|---:|---:|---:|
| 4090 | `98.897%` | `1.103%` | `0%` | `0%` |
| L4 | `98.295%` | `1.705%` | `0%` | `0%` |

Therefore, when evaluating this single-sample verifier, it is recommended to report all three kinds of numbers together:

- `P(reject | BF16)`: the risk of wrongly killing BF16, currently `0.750%` to `2.000%`, with a 4090/L4 equal-weight average of `1.375%`.
- `P(BF16 | reject)`: the risk that it may still be BF16 after seeing a reject, about `0.472%` under the equal prior.
- `P(BF16 | pass)`: the confidence of confirming BF16 after seeing a pass, about `98.600%` under the equal prior.

A single-sample conclusion should be interpreted as a statistical fingerprint-match result, not as a complete identity-attestation proof. High-confidence identity attestation still calls for aggregating multiple probes.
